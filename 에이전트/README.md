# LLM 멀티 에이전트 데이터 검토 (A/B/C/D 실험)

품질 점검 유무 × LLM 에이전트 검토 유무를 비교합니다. 오류 삽입 실험(`../오류실험/`)에서 행 단위 규칙이 놓친 오류(날짜 오기·단위 오류·판매 중복)를 에이전트가 잡는지, 그 결과 재주문 예측이 회복되는지 봅니다.

```
에이전트/코드/
├─ agents.py            집계 도구, 정제 조치 목록, LLM 호출, 역할 4개(분석가 A·B, 조정자, 적대적 검토자)
├─ agent_experiment.py  A/B/C/D(+H) 실험, 중간 기록 저장, HTML 보고서
└─ test_agents.py       단위 테스트 (가짜 LLM 클라이언트, 호출 없음)
```

## 실행

```bash
pip install claude-agent-sdk          # 구독 사용 (기본)
claude auth login                     # 처음 한 번, Claude 계정으로 로그인
cd 에이전트/코드
python -m unittest test_agents
python agent_experiment.py --no-llm   # A·B·H만 (호출 없음)
python agent_experiment.py --pilot    # 교보 1건
python agent_experiment.py            # 두 서점, 오류 0·10·20%, 시드 2개
```

- **호출 방식**
  - 기본은 Claude Agent SDK로 이 컴퓨터의 Claude Code 로그인(구독)을 써서 호출합니다.
  - `--backend api`를 주면 Anthropic API 키(`ANTHROPIC_API_KEY`)로 호출합니다.
  - Windows에서는 SDK가 npm `claude.cmd`를 실행하지 않습니다. 그래서 `claude.exe`를 자동으로 찾습니다(`TBT_CLAUDE_CLI`로 지정 가능).
- **모델**: 기본값은 `claude-opus-5-5`, effort는 `medium`입니다.
- **에이전트 권한**: 파일·셸 같은 기본 도구는 주지 않고, 사용자 설정·메모리도 불러오지 않습니다.
- **다시 실행할 때**: 같은 입력이면 저장된 에이전트 출력(`agent.sqlite`)을 다시 쓰고 호출하지 않습니다.

## 설계

**원자료 보호**: 에이전트는 원본 행과 ISBN을 보지 못하고, 집계 도구 7개의 결과만 받습니다.

| 도구 | 확인하는 것 |
|---|---|
| 표 개요 | 행 수, 기간, 수량 분포, 월별 합계 |
| 키 중복 | 같은 키를 가진 행 |
| 수량 이상값 | 같은 도서 중앙값 대비 수량 배수 |
| 시간 일관성 | 출간 전 기록, 판매와 동떨어진 이벤트 |
| 문서번호-날짜 일관성 | 같은 문서·앞뒤 문서와 날짜가 어긋나는 행 |
| 참조 무결성 | ISBN 오류, 도서정보에 없는 ISBN |
| 표 간 월별 흐름 | 이벤트·반품·판매의 월별 관계 |

도구 결과마다 근거 ID가 붙습니다.

**통제**
- 에이전트는 정제 조치 11종 가운데 고르고 매개변수를 정할 뿐이고, 적용은 코드가 합니다.
- 실제로 받은 근거 ID를 대지 못한 조치는 자동으로 버립니다.

**역할**
1. 분석가 A(표별 분포·중복·이상값)와 B(날짜·문서번호·표 간 흐름)가 서로의 답을 보지 않고 제안합니다.
2. 조정자가 두 제안을 합칩니다. 엇갈리면 도구와 조치 미리보기로 직접 확인합니다.
3. 적대적 검토자가 조치마다 미리보기로 정상 행을 얼마나 건드리는지 확인하고 승인·거부·축소합니다.

**조건**

| 조건 | 내용 |
|---|---|
| A | 점검 없음 |
| B | 기존 품질 점검 |
| C | 에이전트만 |
| D | 품질 점검 + 에이전트 |
| H | 품질 점검 + 고정 휴리스틱(LLM 없이 조치를 정해진 값으로 일괄 적용) |

H는 에이전트의 판단이 조치 목록 자체보다 나은지 보는 대조군입니다.

**지표**
- Precision@20%, AP
- 오류 유형별 처리율(지움 또는 원래 값으로 되돌림)
- 부수 피해(오류가 아닌 행을 지우거나 바꾼 수)
- 실행당 비용(구독이면 API 환산 추정치)

**중간 기록**: 실행 폴더 하나에 아래 파일이 쌓입니다. 원자료 행은 들어가지 않으므로 이 폴더를 그대로 클라우드에 보관할 수 있습니다.
- `run.log`: 단계별 진행 기록
- `config.json`: 실행 설정
- `agents/<사례>.json`: 사례별 에이전트 기록(독립 답변, 조정, 검토 판정, 근거, 최종 조치)
- `results.json`, `index.html`: 사례마다 갱신되는 결과
- `agent.sqlite`: DB 사본
- `manifest.json`: 파일 목록과 SHA-256

## LLM 없이 확인한 것

고정 휴리스틱(H)의 득실은 서점 자료의 성격에 따라 갈렸습니다.
- 예스24: 날짜 오기 대부분을 원래 날짜로 되돌렸습니다.
- 교보문고: 오류가 없는 자료에서도 정상 기록 수백 행을 바꿔 예측 성능을 떨어뜨렸습니다. 교보문고 입하 문서번호는 날짜가 다른 거래에도 다시 쓰이기 때문입니다.

에이전트가 도구 결과에서 이 차이를 읽고 조치를 고르거나 거부하는지가 C·D 조건에서 볼 핵심입니다. 에이전트 실행 결과는 실험이 끝난 뒤 추가합니다.

## 개선 공정 (`improve.py`): 경쟁·토론으로 예측 자체를 개선

데이터 정제만으로는 예측 성능을 되찾을 폭이 작았습니다. 그래서 에이전트가 **예측을 개선하는 안**을 내고, 그 안을 서로 경쟁·토론·검토하는 공정을 만들었습니다. 모든 단계의 입력·중간·최종 산출물이 서점별 공정 DB(SQLite)에 저장됩니다.

| 단계 | 하는 일 |
|---|---|
| 0 분석 | 기준 모델 성능, 변수 중요도, 오답 구간, 달력 월별 재주문률 같은 집계를 DB에 씁니다. 진단표는 채점 구간과 겹치지 않는 앞선 자료로만 계산합니다 |
| 1 경쟁 | 에이전트 A(변수 중심)와 B(모델·학습 기간·정제 중심)가 DB를 읽고(읽기 전용 SELECT) 서로의 안을 모른 채 개선안을 냅니다 |
| 채점 | 코드가 롤링 검증으로 채점합니다. 시험 직전 6개월씩 3구간이고, 구간마다 그 이전 자료로만 학습합니다. 기준 대비 차이, 짝지은 부트스트랩 표준편차, 개선 확률, 기준보다 나은 구간 수를 계산합니다 |
| 2·3 토론 | 점수표와 상대 안을 읽고 반박·결합한 수정안을 냅니다(수정 최대 2회) |
| 4 적대적 검토 | 미리 정한 채택 기준과 과정상의 편향(검증 자료로 고른 변수, 여러 번 시도한 데서 오는 운)을 따져 최종안을 고릅니다. 수치 주장은 근거 ID의 조회 값과 코드가 대조합니다 |
| 5 최종 | 단계별 대표안(기준 / 에이전트 1명 / 경쟁 / 토론 / 검토)을 시험 구간에서 한 번씩 평가합니다. 최종안으로 다음 달 재주문 예상 도서 목록을 만듭니다 |

**공정한 비교를 위한 장치**
- 개선안은 정해진 형식으로만 냅니다(변수 묶음 6종, 모델 설정, 학습 기간, 정제 조치). 적용은 코드가 합니다.
- 변수 묶음은 모두 기준일 이전 기록만 씁니다(테스트로 확인).
- 평가 도서와 정답은 항상 원자료로 고정합니다.
- 에이전트는 시험 결과와 추천 목록을 조회할 수 없습니다.

**중간 관찰**
- 첫 실행에서 적대적 검토자가 검증 점수가 가장 높았던 안을 거부했습니다. 이유는 "검증 구간에서 잰 변수 중요도로 변수를 골랐으니 점수가 낙관적으로 부풀었다"였습니다. 실제로 그 안은 시험 구간에서 기준보다 낮았습니다.
- 이 관찰을 계기로 진단표와 채점 구간을 분리하고 롤링 검증을 도입했습니다. 진행 중 생긴 문제와 해결 과정은 `../트러블슈팅.md`에 있습니다.

```bash
cd 에이전트/코드
python -m unittest test_improve
python improve.py --no-llm     # 0단계만 (호출 없음)
python improve.py              # 두 서점
```
